# 記事生成の再開準備：公式情報取得と広告台帳

このPRは**再開の第1段階**です。広告台帳の検証、公式ページの取得、根拠候補の保存、準備レポートを実装します。AI本文生成、定期実行、記事PRの自動作成、本番公開は行いません。既存の停止版generate_draft.pyと週次点検は変更しません。

## 公式情報取得の仕様

出典はops/official_sources.jsonへ登録し、広告案件IDと対応させます。初回対象はオンスクの公式料金案内と公式機能比較の2URLだけです。[1] [2] 価格をJSONに固定せず、実行時に本文を取得します。対応ホストはコード上でonsuku.jpとfaq.onsuku.jpに限定しており、対象追加には設定とコードのレビューが必要です。

取得するのはrobots.txtと登録済み公式ページのHTMLまたはテキストだけです。画像、JavaScript、広告クリックURL、バナー、計測ピクセルは取得・実行しません。HTTPS、通常の443ポート、許可済みホストを要求し、URL内のID・パスワードや広告追跡パラメータを拒否します。DNSで非公開IPを検出した場合も停止します。ただしDNS検査は事前確認で、接続先IPの固定まで保証するものではありません。

robots.txtを確認し、取得禁止なら停止します。robotsの404は規則なしとして扱いますが、403・429・通信失敗などでは取得を止めます。通常本文はHTTP 200、許可したContent-Type、正常に復号できる文字コードを要求します。リダイレクトは同一ホストでもすべて拒否します。ログイン、CAPTCHA、JavaScript実行での回避は行いません。空の本文も停止条件です。

1リクエストのタイムアウトは10秒、本文上限は1MiB、robots上限は200KiBです。1出典につき最大2リクエストで、初期試験の2出典は順に取得します。圧縮応答を拒否し、環境のプロキシ設定は使いません。外部CSSによる表示状態を完全に判断する処理はありません。

保存項目は出典ID、要求URL、最終URL、HTTP状態、実際の取得日時、HTML本文のSHA-256、抽出テキストのSHA-256、テキスト、robots確認状態です。本文からscript・style等を除きますが、取得テキストは命令として信用しません。

**取得成功は、料金の正しさや規約適合を確認したという意味ではありません。** 出典データにはfact_verification=not_performed、trusted_for_instructions=falseを付け、準備レポートもfacts_verified=falseのままです。公式ページ間の料金・決済条件・解約条件の矛盾判定や、価格とプランの対応付けは次段階です。

## 情報の鮮度と根拠保存

初期設定では料金の根拠を取得後24時間、機能の根拠を取得後168時間までの候補として扱います。これは運営上の上限であり、期間内に公式情報が変わらない保証ではありません。公開前に価格・条件を再確認します。キャンペーンは今回の対象外です。

取得日時はページの更新日や記事の公開日とは別に記録します。ハッシュは同じ根拠を参照しているか確認するためで、情報の真偽を証明するものではありません。現在のコマンドは過去の根拠を読まず、取得失敗時に古い価格へ切り替えません。

取得データとレポートはリポジトリ外の新しい一時フォルダにだけ保存します。既存データがあるフォルダは拒否します。手動のGitHub ActionsではRUNNER_TEMPへ出力し、Artifactsの保持期間は14日です。本文をサイトへ転載したり、公開リポジトリにコミットする処理はありません。保存するのは公開公式情報だけで、ASP管理画面の私的情報をArtifactsへ入れません。

## 広告台帳の仕様

ops/affiliate_registry.jsonには、既存5案件を登録します。オンスク.JP、PC WRAP、シェフの無添つくりおき、SwitchBot、ExpressVPNです。現在の対象記事にある広告はA8.netです。afbやドコモの新しい案件・リンクを、このPRで推測して追加することはありません。

各案件はid、name、aspに加え、approval（提携状態）、conditions（掲載条件の確認状態）、automated_use（準備で扱う範囲）、assets（既存広告の参照）を持ちます。

approval.statusはapprovedとして、運営者が2026年11月11日に既存案件をすべて承認済みと申告した事実を登録します。verification_methodで運営者申告と画面確認を区別し、scopeはexisting_siteとします。ASPの承認状態をAPIで照合する機能はありません。

conditions.statusは、オンスクについてowner_reviewedとし、確認範囲を公開承認されたPR #4の個別改稿と記録します。他4案件はpending_recordingです。**提携未承認という意味ではなく、個別の掲載条件が台帳へ未登録という意味です。** オンスクの確認も将来の全記事・全表現の無条件承認とは扱いません。

assetsには既存記事のパスと、広告要素の原文から計算したSHA-256指紋・要素数を保存します。リンクを新しく発行したり、広告コードを台帳へ複製したりしません。広告URLを含むタグ、A8関連属性、検出できる広告用インラインスクリプトが変わった場合は準備を停止します。指紋の更新で無断変更を隠してはいけません。これは静的コードの照合であり、成果計測や画像表示の成功を保証しません。

パスは既存のルートHTMLファイル名に限定し、存在しない記事、パスの逸脱、シンボリックリンクを拒否します。初回テーマはオンスク既存記事の取得準備だけで、HTMLを書き換えません。

ASP会員情報、成果報酬・売上、APIキー、秘密の掲載条件全文は公開台帳に保存しません。今後、私的条件の管理が必要なら、非公開の保管先を決めてから導入します。提携失効・掲載条件変更の自動検知も、現段階では未実装です。

## 実行方法と停止条件

ローカルの読み取り専用準備は、リポジトリのルートで次を実行します。

```bash
python3 ops/prepare_generation.py
```

このコマンドはネットワーク通信をせず、台帳・広告コード・テーマの対応を検査して一時フォルダにレポートを出します。公式ページの取得も試す場合は次です。

```bash
python3 ops/prepare_generation.py --fetch
```

記事は生成されず、価格確認済みにはなりません。台帳やテーマの不備は終了コード2、公式情報の取得失敗は3で停止します。取得が成功しても、状態はsources_acquired_pending_claim_and_model_reviewです。

マージ承認後に手動実行する場合は、GitHubのActions → Generation Preparation (No Article or Publish) → Run workflowです。fetch_sources=falseでは通信せず、trueでは登録済み公式ページを取得します。このワークフローに週次スケジュールはありません。contents: readだけを使い、秘密情報、Git書込み、記事PR作成権限は要求しません。準備レポートはSummaryとArtifactsで確認します。

生成状態のenabled、llm_provider_configured、cost_approvedは、この準備版ではfalseに固定し、trueに変えた場合は検証で停止します。フラグだけ戻して本文生成を有効にできる設計にはしません。

## 次段階で実装・承認するもの

次の実装では、各記述を「値、通貨、税込／税別、請求周期、対象プラン、適用条件、出典ID、本文ハッシュ、根拠引用、確認状態」に対応付けます。現在はこの記述単位の事実台帳や自動検証はまだありません。根拠の不足や重大な矛盾を人間の確認へ回し、未使用の体験談や最安値の創作を防ぎます。

週1件上限の設定値は今回登録しますが、生成回数の記録、手動再実行・並列実行のロック、既存slug・未承認PRの重複防止、記事下書きPRの作成は次の段階です。既存topics.jsonのsim-comparisonはpending_draftでもHTMLが既にあるため、そのまま新規生成してはいけません。

AI本文生成の方式・認証・モデル・予算上限は、費用見積もりを示して承認を得ます。今回の準備コードはLLMを呼ばず、有料API・新しい契約・課金ジョブを導入しません。Manusでの現在の準備作業のクレジット消費と、将来の定期生成費用は別です。Sandbox限定のAPI認証をGitHubへコピーしません。

再開機能の実装PRと生成された各記事の公開承認は分けます。mainへの直接push・自動マージは導入しません。停止を検証する既存テストは保持し、実際の再開PRでは新しい安全要件に合わせたテストを追加・更新します。

## このPRの受け入れ確認

人間が広告台帳の案件名・提携状態・確認範囲を確認し、オンスク以外の未登録条件を承認済みと誤認しないことを確認します。公式取得の成功と事実確認の未実装を区別し、安全テストと手動試験の結果を確認してから、この準備PRのマージを承認します。

このPRのマージだけで記事生成は再開しません。Workers停止設定の効果は、新しいPRのチェックで確認します。Workersの本番無効化・プレビュー無効化が画面上で設定されていても、新規ビルドが起動しない実行結果を見るまでは、動作確認完了とは断定しません。
